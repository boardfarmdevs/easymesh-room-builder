EasyMesh research lab · room builder guide

The room builder manual

Design the virtual rooms the EasyMesh optimizer is evaluated in: a floor of any size, walls of any material, the mesh agents and their clients, and the movement, presence and experiment metadata of a scenario. Everything is written in the configurator's own language and compiles to the same wmdcfg.world-plan.v1 as wmdcfg world-compile.

    What the builder does

    The lab's rooms are Golden Worlds: two JSON source documents that the configurator compiles into an RF timeline for wmediumd.

    layout   (wmdcfg.world-layout.v1)  space · propagation · walls · fixed agents and clients
mobility (wmdcfg.mobility.v1)      duration · tick · seed · paths · presence · checkpoints · metadata
                        │ world-compile
                        ▼
world plan (wmdcfg.world-plan.v1)  positions + presence + directed SNR per band at every tick
                        │ world-export --band 2.4|5|6|all
                        ▼
.wmd phase scenario  →  bind / compile / run on the lab's atomic wmediumd control socket

    The builder edits those two documents directly — verbatim, with no extra fields — and keeps builder-only metadata (wall materials, notes, the room guide text) beside them in a roombuilder.design.v1 file. Its compiler is a faithful port of wmdcfg/world.py and geometry.py; the test suite proves that all 50 library rooms compile byte-identically with the reference configurator and that every reference golden world is reproduced, in step with the configurator of 28 September 2026.

    The builder never talks to a live lab. What it shows is the configurator's RF model (the same numbers the lab will apply); association, steering and backhaul parents are decided by the real EasyMesh software once the room is loaded.

    Quick start

    1. Library… opens 50 rooms. The Reference lab rooms are the configurator's golden worlds; the others are new examples (homes, offices, a warehouse, a 100-client arena, stress tests).
    2. Or New…: choose a size and a template. Lab starter adds the gateway, ten static clients and four optimally placed extenders.
    3. Pick a wall material and draw with W (click, click, … Esc), drop a rectangle of walls with R, cut doors with D.
    4. Add agents with E and clients with C, or use Devices → Place extenders optimally.
    5. Select a client and press P; click the floor to add waypoints. Space plays the scenario.
    6. Watch the badge at the bottom right. Check → Run verification runs the full suite; Export… → Lab bundle writes everything the lab needs.
    7. Save (Ctrl+S) keeps the design on the server with a revision history.

    The screen

    • Sidebar — the design card (title, save state, New/Library/Open/Save/Import/Export) and six tabs: Room, Walls, Devices, Motion, Scenario, Check. Drag the divider to resize it; double-click it to reset.
    • Room view — the same scene the room viewer draws: floor with a 2 m grid, translucent walls with their name and loss on the floor, cone agents and sphere clients with their labels and 10-segment signal gauges, the strongest simulated link of each client (dashed, red → yellow → green), backhaul ribbons on the floor and purple trails.
    • Toolbar — tools, camera (3D / Plan / Walk), Fit, undo/redo, Heatmap, Screenshot, Full screen. The strip below it shows options of the active tool (materials, door width, walk speed, snap).
    • Properties panel (dark, draggable) — everything about the selection: position, role, transmit adjustment, wired backhaul, presence and path summary, and a live link table with both directions per band.
    • Timeline — play/pause, time, scrub, speed, band, and (via Lanes) one lane per moving or appearing role with presence bars, waypoint ticks and checkpoints.
    • Check badge — green when the room compiles and is admissible for the selected lab profile; amber for warnings; red when the configurator would reject it. Click it for details.

    Hover or focus any control for an explanation. Tips on configurator properties also show the document they belong to and their constraints.

    Designs, the library, import and export

    Saving

    Designs are stored on the server in the designs/ folder (one JSON file each). Every save keeps the previous version in designs/.history/<id>/ (the newest 40); Open… lists them and can reopen any revision. If the same design was saved from another tab, the save is refused and offered as a copy instead. Your working room is also kept in the browser, so a reload restores it.

    Walls

    In the configurator a wall is a straight segment with one number, loss_db, added on every band each time the straight line between two devices properly crosses it. A material is a builder preset for that number and a drawing style; exported layouts carry only name, start, end and loss_db.

    MaterialLossUse
    Glass / window2 dBglass partitions, meeting rooms
    Drywall3 dBstud partitions, bathrooms
    Interior wall5 dBthe value of every wall in the reference homes
    Solid wood / door6 dBtimber walls, heavy doors
    Brick8 dBsingle-leaf brick or block
    Concrete partition12 dBthe reference courtyard partition
    Reinforced concrete18 dBload-bearing walls, stair cores
    Metal / shaft / racks30 dBlift shafts, racking
    RF isolation70 dBthe reference isolation wall that cuts a relay off
    Customany ≥ 0fractional values are allowed

    Rules worth knowing

    • Standing on a wall's line ignores that wall. A path that starts exactly on a wall (or runs along it) never properly crosses it. The builder keeps new and dragged devices at least 5 cm off wall lines (it moves them 10 cm and tells you) and the Check tab flags existing cases — several reference rooms have them.
    • Doors are gaps. Links through a gap see no wall loss. The Door tool cuts a gap of the chosen width into a wall, turning it into two walls.
    • Double walls. Two parallel walls add both losses. Select a wall and press Double for a copy 20 cm away. Overlapping collinear walls also add both — the checker points them out in case it was an accident.
    • Walls on the room boundary change nothing: every device is inside the room. Exterior walls matter around gardens, courtyards or L-shaped footprints inside the room.
    • Walls are band-independent in this model; real materials attenuate 5 and 6 GHz more than 2.4 GHz.

    Precision drawing

    • Plan view (T) is an exact orthographic top view; plan +y points up.
    • Points snap to the grid (Room → Editing → Snap grid), to other wall ends, onto existing walls (T-junctions) and to the room edges. Alt disables snapping, Shift constrains to 15° steps.
    • While drawing, type a length (e.g. 3.6) and press Enter for a wall of exactly that length toward the cursor. Clicking the first point closes the outline.
    • Select a wall to drag it, drag its purple end handles, or type start/end coordinates, length and angle in the properties panel.

    Agents and clients

    Every device is a role. In the lab each role is bound to a container: gateway → bpibroadband (Agent-1), extender_1..4 → bpiap…bpiap-003, sta_static_01..10 and sta_mobile_01..10 → the twenty named clients, sta_pool_021..100 → the 100-client pool. Roles are physical identities: moving sta_static_03 moves the container bound to it; roles never follow association.

    • E adds an agent: the first is gateway, then extender_1, extender_2…
    • C adds a static client using the next free lab role; Shift-click adds a mobile one. Add N clients places many at once (grid, scattered, or clustered around the selection).
    • The viewer colours clients by role name: purple only when the name contains mobile. A moving sta_static_… is legal (the band rooms do it) but is drawn dark.
    • Wired backhaul (backhaul: "wired", agents only): the AP's LAN port is on the controller's LAN, so it needs no Wi-Fi backhaul. It still has AP-to-AP links and can be a Wi-Fi extender's backhaul parent; the lab gives those links RF only when the AP's own backhaul station never connects (wired_guard). The builder treats it as a root of the backhaul tree, like the gateway. The lab's wired extender is extender_5 (bpiap-004).
    • Transmit adjustment (tx_gain_db_by_band) is added to every link the role transmits. A negative value on a client makes its uplink weaker than its downlink — an asymmetric link.
    • Park keeps a lab role in the room but never on air (presence: []). Use it for spare extenders in small homes: the lab requires every mesh role to be present in the world.

    Optimal extender placement

    Devices → Place extenders optimally chooses positions for N extenders using the configurator's propagation model:

    • Each sample point scores its best AP→point SNR on the chosen band with a utility that rises linearly from target − 25 dB to the target and keeps a small bonus above it. Samples are a floor grid, every client position over the whole scenario, or both with equal weight.
    • Every placed extender must reach the gateway through Wi-Fi hops whose weaker direction is at least the backhaul threshold (default 20 dB on 5 GHz). Wired extenders and pods neither need nor provide such hops.
    • Extenders keep 30 cm from walls and room edges and a minimum spacing between agents.
    • Search: greedy selection over a candidate grid, candidate swaps, then pattern-search refinement down to the configurator's 5 cm quantum. It is deterministic.
    • Replace re-positions the existing extenders (keeping their roles); Add keeps every AP and adds new roles. The proposal is shown as purple ghosts with their backhaul hops; Apply writes it as one undo step.

    The heatmap (H) shows the same field: best AP→point SNR on the selected band, in the signal meter's bands (red < 16 dB, yellow 16–35 dB, green ≥ 36 dB) or continuous. The cursor readout at the bottom left names the best AP and its SNR under the pointer.

    Motion, presence and playback

    The script

    • duration_ms must be a whole number of ticks; the builder rounds and says so.
    • tick_ms (100 ms – 60 s) is one RF generation. A fast walk with a long tick jumps between generations; the checker points this out.
    • seed selects the seeded shadowing sequence (only relevant when shadowing σ > 0).

    Paths

    • Path tool (P): click a client, then click the floor; each waypoint's time is the distance divided by the walk speed. Backspace removes the last waypoint, Enter finishes. Clicking empty floor first creates a new mobile client. If the path runs past the end, the script is extended.
    • Keyframes: scrub to any time and drag a moving client — a waypoint is inserted at that time (or the existing one moved). Alt-drag moves the whole path.
    • Selecting a mobile client shows its path with a purple ring and time label per waypoint; drag the rings. The Motion tab lists waypoints with editable times and coordinates.
    • Retime at … m/s makes the speed constant while keeping dwells; Dwell +5 s holds at a waypoint; Templates generate a room loop, a cross-and-back walk, a border hover (ping-pong test) or a seeded wander.
    • Agents may move too (extender evacuation, backhaul parent handover): Make movable.

    Positions interpolate linearly between waypoints; after the last one the role holds still. The first waypoint is always at 0 s.

    Presence

    Presence is a list of half-open [start, end) spans when the role is on air. While absent, every link of the role is the SNR floor. For an extender this removes its fronthaul; the live lab keeps the container running. Use Disappear/Appear from here, Always, Park, or edit the spans.

    Checkpoints and backhaul policy

    • pause_at_ms: playback stops at each checkpoint — here and in the live room — so the optimizer can measure stable RF. They are viewer/room metadata; .wmd exports do not contain them.
    • backhaul_rf: fixed (default) keeps the lab's protected startup backhaul; geometry makes AP-to-AP RF follow the room during loading, playback and dragging, with native parent selection.

    Scenario metadata

    • Band-steering profiles (band_steering): at most four initially present clients with allowed_bands, an initial_band among them and optionally measurement_mode: "received_same_band" (exactly one allowed band; the optimizer then uses AP→client passive reception).
    • Expectations (band_steering_expectations): signed checkpoints {time_ms, roles: {role: {band, ap}}} stating where profiled clients should end up. + at t pre-fills the predicted best AP.
    • AP expectations (ap_expectations): which AP each named client must be on at the final settle or at a checkpoint, e.g. [{"at": "final", "roles": {"sta_mobile_01": "extender_5"}}]. Removing a checkpoint drops an expectation pinned to it.
    • Traffic experiment (traffic_experiment, schema easymesh.room-traffic.v1): 1–4 ordered phases inside the first 60 s, each ≤ 20 s, from an initially present client, payload 64–1200 bytes; ICMP 1–200 packets/s or UDP 0.1–12 Mbps with at most 2000 datagrams/s.
    • Room guide: the four texts of the viewer's “Browse rooms · RF & optimizer guide” (Simulated RF, Expected optimizer behavior, Evidence to check, What this does not prove). The lab bundle includes them as a room-guide entry.

    The RF model

    For band b, the directed link from source to destination at a tick is

    clamp( round( reference_snr[b]
              − 10 · n · log10( max(d, d0) / d0 )
              − Σ loss of walls the straight path properly crosses
              + source transmit adjustment[b]
              + seeded shadowing(seed, tick, unordered pair, band, σ) ),
       floor, ceiling )
    • round is Python's round-half-to-even: 42.5 → 42, 43.5 → 44. The browser model reproduces it.
    • Closer than the reference distance d0 there is no path loss.
    • An absent role has the floor value on all its links.
    • Presets: Home/office 54/50/47 dB at 1 m, n = 2.2 (every home, lane and large-room reference layout); Courtyard 52/48/45 dB, n = 2.8 (the backhaul rooms); Open hall n = 2.0; Dense office n = 3.0.
    • The live preview (links, gauges, heatmap, link table) is exact except for shadowing, which is a zero-mean seeded term applied only in the compiled world.
    • Signal colours use the viewer's meter with a fixed −91 dBm noise reference: red below 16 dB, yellow 16–35 dB, green from 36 dB.

    Checking a room

    Live findings

    Every change is linted on the server: configurator errors (what world-compile would reject, with the offending role or wall selected on click), lab admission problems for the chosen profile, and pitfalls the configurator accepts silently: devices on wall lines, walking along a wall, stacked walls, fast motion for the tick, early-stopping paths, coverage holes (< 10 dB), weak extender backhaul, rooms smaller than the viewer's 20 × 14 m default, moving clients that the viewer will colour as static.

    World plan — wmdcfg.world-plan.v1

    Compiled output: name (layout--mobility), layout_sha256, mobility_sha256, tick_ms, duration_ms, bands, counts, roles, wired_backhaul, walls, the metadata above and one generation per tick with positions (1 mm), present and every directed link (link_class, distance_m, wall_loss_db, snr_db_by_band), plus golden_sha256 over the canonical JSON. It does not record the room size or propagation.

    Taking a room into the lab

    1. Export the Lab bundle and unzip it.
    2. Copy worlds/layouts/*.json, worlds/mobility/*.json and worlds/golden/*.world.json into configurator/worlds/ of easymesh-medium, where the labs' rooms live.
    3. Add the line from build-goldens.emit to worlds/build-goldens.sh and run worlds/build-goldens.sh --check: it recompiles the room from its sources and must find the same bytes.
    4. Optionally add room-guide-entry.js to the viewer's room-guide.js and the world ID to the viewer's list, then load it in the room like any golden world.
    The live room binds roles to containers: use a lab profile while designing and keep the Check badge green. More than 20 clients need a lab provisioned with the 100-client pool.

    Command line and API

    ./room-builder serve [--port 8790] [--data designs/] [--reference /path/to/easymesh-medium]

./room-builder export ROOM --format layout|mobility|world|wmd|bundle|svg|dxf|design [--band all] -o OUT

    ROOM is a design file, a layout (plus mobility) file, a compiled .world.json, or a library room id. The JSON API behind the UI is listed in the README (/api/lint, /api/compile, /api/verify, /api/place, /api/coverage, /api/import, /api/export/<kind>, /api/designs…, /api/library…).

    Limits

    • One floor per room (no multi-storey propagation), straight walls, band-independent wall loss — exactly what the configurator models.
    • The preview omits seeded shadowing; the compiled world includes it.
    • The optimizer maximises modelled coverage with a signal-only backhaul guard; it does not model capacity, channel planning or interference.
    • Nothing here proves steering: the lab's native software and optimizer decide associations once the room is loaded.
